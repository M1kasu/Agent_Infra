> 本文档根据 GOAI 世界人工智能开源大赛官网 **Agent Infra 新智基座** 赛道页面整理。
> 整理日期：2026-08-14
> 官方页面：https://www.goaihz.com/tracks?track=infra
>
> 本文档以“便于项目开发、Codex 执行和赛前验收”为目标进行结构化整理，并非官方原文逐字转载。若赛事规则后续调整，以官网和组委会最新通知为准。

---

## 1. 赛道定位

**Agent Infra 新智基座**聚焦企业级复杂任务场景下的：

- 多 Agent 基础设施；
- 多 Agent 协同系统；
- Skill 能力沉淀；
- 外部工具与企业系统集成；
- 任务执行验证；
- 执行证据沉淀；
- 安全、审批、回滚与审计；
- 可复用、可迁移、可开源的 Agent Infra 能力。

赛道核心目标是推动 Agent 从简单 Demo 走向可用于真实企业场景的 Production 级系统。

参赛作品不能只展示“一个 Agent 会回答问题”，而要体现多个 Agent 在复杂约束下如何共同完成真实任务。

# 2. 核心硬性要求

以下要求建议作为项目开发过程中的最高优先级验收项。

## 2.1 至少 3 个不同职能 Agent

参赛方案必须设计：

```text
>= 3 个不同职能 Agent
```

每个 Agent 应具有：

- 清晰身份；
- 明确职责；
- 能力边界；
- 输入与输出；
- 协同关系；
- 上下游关系；
- 工具 / Skill 使用范围。

多个 Agent 需要协同形成完整的端到端任务闭环，不能只是把一个 Agent 拆成多个名字。

---

## 2.2 AgentTeams 为必选协同设计基点

多 Agent 协同设计必须以：

```text
AgentTeams（原名 HiClaw）
```

作为设计基点。

项目需要明确说明以下能力如何映射到 AgentTeams：

- 角色编排；
- 任务拆解；
- 上下文传递；
- Agent 间协同；
- 协同执行；
- 状态追踪。

不能仅在 README 或 PPT 中写“使用 AgentTeams”，而没有真实的架构映射与协作逻辑。

### 初赛

初赛以方案设计为主，可以重点说明 AgentTeams 的架构映射。

### 复赛

需要提交可执行的 AgentTeams 代码包，并提供可运行 Demo 或 Demo 视频。

---

## 2.3 必须提交 Agent Identity 清单

项目需要准备完整的：

```text
Agent Identity
```

建议至少说明：

| 字段 | 说明 |
|---|---|
| Agent Name | Agent 名称 |
| Identity | 身份定位 |
| Responsibility | 核心职责 |
| Inputs | 输入 |
| Outputs | 输出 |
| Skills | 使用的 Skill |
| Tools | 可调用工具 |
| Permissions | 权限范围 |
| Context / Memory | 可访问上下文 |
| Risk Boundary | 风险边界 |
| Upstream | 上游 Agent |
| Downstream | 下游 Agent |
| Failure Strategy | 失败处理 |

正式提交格式还需参考参赛手册附录 A。

# 3. 多 Agent 完整闭环要求

参赛方案需要说明多个 Agent 如何共同完成完整任务。

至少应覆盖以下过程。

## 3.1 任务输入

系统应能够接受企业实际任务输入，例如：

- 告警；
- 工单；
- 日志；
- 账单；
- 安全事件；
- 企业业务事件；
- 用户请求；
- 其他结构化或非结构化任务输入。

---

## 3.2 任务拆解

由：

```text
主控 Agent / Manager Agent / 协同框架
```

将复杂任务拆解成多个子任务，并分配给不同职能 Agent。

需要体现：

- 为什么拆；
- 拆给谁；
- 子任务之间的依赖；
- 并行 / 串行关系；
- 失败后的重新规划。

---

## 3.3 上下文传递

不同 Agent 之间需要能够传递：

- 原始任务；
- 任务状态；
- 历史信息；
- 中间结论；
- 工具调用结果；
- 检索证据；
- 执行结果；
- 风险信息。

建议尽量采用结构化上下文，而不是完全依赖自由文本聊天。

---

## 3.4 工具调用

Agent 应能够调用：

- Skill；
- MCP 工具；
- 云产品；
- 企业系统；
- 数据库；
- 知识库；
- CI/CD；
- 监控系统；
- 外部 API；
- 其他业务工具。

重点不是“有没有工具调用”，而是工具是否真正参与任务闭环。

---

## 3.5 结果验证

系统不能仅以：

```text
Tool Call Success
```

作为任务完成依据。

需要验证：

- 修复是否真正生效；
- 安全处置是否真正完成；
- 成本优化是否达到目标；
- 业务状态是否达到预期；
- 任务是否真正闭环。

典型链路：

```text
Execute
  ↓
Observe
  ↓
Verify
  ↓
Success / Retry / Replan / Rollback
```

---

## 3.6 执行证据沉淀

系统应保存可以证明任务真实执行过的证据，例如：

- Log；
- Trace；
- Metrics；
- 运行报告；
- 工具调用记录；
- 截图；
- 输入输出；
- 测试结果；
- 审批记录；
- 审计记录；
- 其他执行证据。

---

## 3.7 审批、回滚和审计

涉及高风险行为时，系统需要设计：

- 人工确认；
- 人工审批；
- 权限边界；
- 风险分级；
- 回滚；
- 审计；
- 降级策略。

高风险动作不能默认全部由 Agent 自动执行。

---

## 3.8 经验沉淀

任务执行完成后，应考虑将：

- 处理结果；
- 失败原因；
- 复盘内容；
- 经验规则；
- Runbook；
- 历史案例；

沉淀为后续可复用能力。

---

# 4. Skill 要求

## 4.1 Skill 是必选项

比赛明确要求：

```text
Skill = 必选
```

参赛项目可以：

- 使用阿里云官方用云 Skills；
- 自行将项目关键能力抽象为可复用 Skill；
- 两者结合。

Skill 应是：

```text
可复用的任务能力抽象层
```

而不是仅描述某一次 Agent 行为。

---

## 4.2 每个核心 Skill 至少需要说明

- Skill 名称；
- Skill 用途；
- 输入；
- 输出；
- 调用条件；
- 依赖工具；
- 失败处理；
- 安全边界；
- 复用价值；
- 与多 Agent 协同流程的关系。

建议进一步工程化定义：

```text
name
version
description
input_schema
output_schema
preconditions
postconditions
dependencies
timeout
retry_policy
risk_level
failure_handling
validation
audit_fields
```

---

# 5. MCP 与工具集成要求

## 5.1 MCP 为推荐项，不是强制项

MCP 适合连接：

- 云产品；
- 企业系统；
- 数据库；
- 知识库；
- 工单平台；
- CI/CD；
- 监控系统；
- 外部工具。

比赛推荐采用：

```text
Skill = 能力抽象层
MCP   = 工具连接层
```

---

## 5.2 不使用 MCP 时的要求

如果项目没有使用 MCP，需要提供等价的外部工具集成契约。

至少需要说明：

- 协议；
- 鉴权方式；
- 工具名称；
- 调用入口；
- 参数 Schema；
- 返回结构；
- 权限范围；
- 错误处理；
- 失败重试；
- 幂等控制；
- 审计日志；
- 降级方式；
- 后续迁移到 MCP 的成本。

评审需要能够判断：

> 未来迁移到 MCP 时是否只需做协议适配，而不是重新设计整套工具调用链。

---

# 6. RAG、记忆、共享状态与上下文增强

RAG 为推荐项，并非强制。

可用于：

- 企业知识库；
- 历史任务；
- 标准规范；
- Runbook；
- 业务数据；
- 评审证据；
- 工具执行结果；
- 历史案例。

推荐链路：

```text
MCP / Tool
    ↓
数据源
    ↓
Skill
    ↓
检索 / 证据对齐
    ↓
Agent
    ↓
判断证据是否足够支撑决策
```

---

## 6.1 上下文增强硬要求

参赛方案需要从以下 4 项能力中：

```text
至少实现 2 项
```

四项分别为：

- Agent 记忆存储；
- 知识库 RAG；
- 共享状态管理；
- 轨迹可观测。

### 如果不使用 RAG

则必须从剩余三项中：

```text
至少实现 2 项
```

即：

- Agent 记忆存储；
- 共享状态管理；
- 轨迹可观测。

并说明上下文机制为什么有效。

---

# 7. 可观测要求

可观测为推荐项，不强制，但属于 Agent 从 Demo 走向 Production 的重要能力。

建议覆盖：

- Skill 调用；
- MCP 工具；
- RAG 检索；
- LLM 推理；
- Agent 协作；
- 状态流转；
- 重试；
- 回滚。

---

## 7.1 推荐观测数据

至少考虑：

```text
Trace
Log
Metrics
```

若使用可观测能力，建议覆盖其中 1～2 类以上。

还应说明：

- 数据如何采集；
- 是否遵循 OpenTelemetry / GenAI 等语义规范；
- 数据类型；
- 后端存储；
- 检索方案；
- 使用场景；
- 带来的效果。

建议基于观测数据进行：

- 在线评估；
- 离线评估；
- Agent 效果量化；
- Agent 效率量化；
- 性能优化；
- 成本分析。

- 为什么替换；

- 可替换性；
- 权限边界；
- 后续迁移成本。

---

## 8.1 禁止“为了比赛堆技术”

比赛评审不会按照：

```text
用了多少个推荐产品
```

来打分。

重点是：

```text
设计理念
+ 接口契约
+ 必要性
+ 可替换性
+ 权限边界
+ 端到端闭环证据
+ 后续迁移成本
```

因此项目应优先保证核心链路真实可运行。

# 9. 开放式选题

比赛不限定必须做运维、安全或成本治理。

只要：

- 来源于真实需求；
- 具有一定行业普遍性；
- 能体现多 Agent 价值；
- 可以进行任务拆解；
- 可以协同执行；
- 可以调用工具；
- 可以验证结果；
- 可以沉淀经验；
- 有潜力形成复用 Skill / 工具接口 / 开源能力；

都可以作为有效选题。

# 12. 初赛阶段：方向与方案设计

初赛重点评估：

- 项目方向；
- 技术方案；
- 开放 / 开源价值；
- 可行性。

> **初赛不强制要求提交可运行代码。**

## 12.1 初赛提交材料

| 提交材料 | 是否必交 | 形式要求 | 内容说明 |
|---|---|---|---|
| **作品简介** | **是** | 文字说明（500 字以内） | 项目名称约 20 字；说明问题与场景、核心解决方案、创新点与差异化优势、开放 / 复用价值、当前进展。 |
| **方案 PPT** | **是** | PPT / PDF | 建议展开场景与价值、方案设计、Skill 与工具集成、可行性与落地计划，说明 Agent 分工、任务拆解、上下文传递、结果验证、异常分支、安全边界、风险控制和开放 / 开源计划。 |
| **可执行 AgentTeams 代码包** | **可选** | 仓库链接 / 压缩包 | 非强制；若提交，应包含运行入口、依赖说明、配置文件、样例输入输出和运行证据。 |

## 12.2 初赛阶段重点

初赛阶段应优先把以下内容讲清楚：

```text
真实场景与用户痛点
        ↓
为什么需要 Multi-Agent
        ↓
Agent 分工与任务拆解
        ↓
AgentTeams 协同设计
        ↓
Skill 与工具集成
        ↓
结果验证与异常处理
        ↓
安全边界与风险控制
        ↓
开放 / 开源与复用价值
```

因此初赛阶段的首要目标不是堆大量工程实现，而是证明：

1. **场景成立**：确实存在真实、具有代表性的企业问题；
2. **Multi-Agent 有必要**：不是一个普通单 Agent 就能自然完成；
3. **方案闭环**：从任务输入到执行、验证、异常处理形成完整链路；
4. **AgentTeams 可落地**：Agent 分工和协同关系能够映射到 AgentTeams；
5. **Skill 可复用**：核心能力能够沉淀为独立 Skill，而不是只服务单一 Demo；
6. **工程实现可行**：进入复赛后能够实现为可执行系统。

# 15. 评分标准

总分：

```text
100%
```

## 15.1 场景价值与行业可复制性：25%

重点看：

- 场景是否真实；
- 问题是否明确；
- 是否具有代表性；
- 目标用户是否清楚；
- 痛点是否真实；
- 是否产生可感知价值；
- 是否提升效率；
- 是否降低成本；
- 是否改善质量；
- 是否优化体验；
- 是否控制风险；
- 是否沉淀知识；
- 能否向其他行业 / 组织 / 流程迁移。

---

## 15.2 多 Agent 协同与自主闭环：25%

重点看：

- Agent 职责是否清晰；
- 任务拆解是否合理；
- 上下文传递是否结构化；
- 协作协议是否清楚；
- 状态流转是否清晰；
- 是否处理异常；
- 是否处理冲突；
- 是否支持多方案选择；
- 高风险动作是否有人审；
- 是否支持回滚；
- 是否具有审计边界。

---

## 15.3 Skill 工程体系与生态复用：25%

重点看：

- Skill 是否覆盖关键能力；
- 输入输出是否明确；
- 调用条件是否明确；
- 依赖工具是否明确；
- 失败处理是否明确；
- Skill 是否可复用；
- 是否支持多个 Agent；
- 是否支持多个场景；
- 是否考虑版本；
- 是否考虑发布；
- 是否考虑回滚；
- 是否考虑质量评估；
- 是否以 AgentTeams 为协同基点；
- 是否合理使用官方 Skills。

---

## 15.4 工程落地、运行验证与安全可审计：20%

重点看：

- 配置是否清楚；

- 是否有审批；
- 是否有回滚；
- 是否有降级；
- 是否有审计。

---

## 15.5 开放 / 开源贡献：5%

重点看：

- 是否形成可复用成果；
- 是否有接口契约；
- 是否有文档；
- 是否有示例；
- 开源协议是否清晰；

# 25. 开发优先级建议

```text
P0 真实场景价值
        ↓
P1 AgentTeams + Multi-Agent 闭环
        ↓
P2 Skill 工程体系
        ↓
P3 Tool / MCP
        ↓
P4 Verification
        ↓
P5 Safety / Approval / Rollback / Audit
        ↓
P6 Shared State / Memory / RAG / Observability
        ↓
P7 Demo + Evaluation + Evidence
        ↓
P8 UI 与其他扩展能力
```

不要反过来为了视觉效果或技术数量牺牲核心闭环。
