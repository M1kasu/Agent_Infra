# 00 · Product Proposal

## 项目名称

**OfficeOps Agent｜企业数字办公 IT 运维多 Agent 协同系统**

## 产品定义

OfficeOps 服务的是企业**办公侧 IT 运维**——保障员工在身份、协作应用、设备与网络上正常工作的 IT 服务与支持，区别于面向生产系统与基础设施的 SRE 运维。参与角色与系统的关系分三类：

- **服务对象**：企业全体员工——在钉钉/OA/ITSM 报障或发起申请，是任务的请求者与受益者，不操作系统；
- **直接用户**：IT 服务台与桌面运维——人工跨后台排查、执行、回访的人，OfficeOps 自动化的是他们的重复劳动；
- **治理参与者**：系统/网络管理员与信息安全人员——系统的约束与安全兜底。

来自钉钉、OA、ITSM、监控或生命周期事件的办公 IT 任务，交给多个职责和权限不同的 Agent 协同处理：理解问题、采集证据、诊断或规划、按风险审批、执行工具、验证结果并沉淀经验。
产品不是“连接越多越好”的万能聊天助手，而是一套可扩展的企业运维协同底座：

> 用统一 WorkItem 和 ManagedObject 描述不同办公任务，用场景 Skill 表达专业能力，用 MCP/Tool Adapter 连接厂商系统，用 AgentTeams 管理协作和状态，用 Evidence/Verification 证明任务真正完成。

## 场景边界

| 场景域 | 典型任务 |
| --- | --- | :--: |
| 设备与空间 | 打印机离线、会议室无法投屏、终端故障 |
| 协作与 SaaS | 钉钉登录、邮箱发送、Docs/OA 访问异常 |
| 身份与访问 | SSO 认证、VPN 账号/资源、应用权限 |
| 网络 | Wi-Fi、DNS、远程接入、办公网访问 |
| 基础设施依赖 | 支撑办公服务的云服务器、容器、K8s 工作负载 |

这张表表达的是长期愿景：办公 IT **从打印机到钉钉的横向贯通**。交付策略与之配套——**横向定义、纵向跑深**：横向以 Core / Scenario Pack / Adapter 三层架构保证新场景可低成本复制；纵向在初赛只把 Docs 访问故障一个场景做到含异常分支与输入变体的完整闭环，其余场景以场景包映射呈现，不在本期实现。

## 十个核心问题

| # | 问题 | 回答 |
| :- | :-- | :-- |
| 01 | 我们做什么？ | 构建企业数字办公 IT 运维的多 Agent 协同、能力复用、工具接入和运行验证底座。 |
| 02 | 谁使用？ | 三类关系（见产品定义）：服务对象=全体员工；直接用户=IT 服务台/桌面运维 L1；治理参与者=系统/网络管理员、资源负责人、安全审批与审计。 |
| 03 | 何时使用？ | 员工报障、服务申请、账号/权限变更、资产异常、办公服务告警和入转离事件。 |
| 04 | 当前怎么做？ | 人工接收自由文本，反复询问，跨多个后台查状态，根据个人经验判断并操作，再手工回复和记录。 |
| 05 | 核心痛点？ | 上下文分散、专业域多、权限边界复杂、操作依赖人、结果缺少独立验证、经验难沉淀。 |
| 06 | 产品价值？ | 缩短定位和处理时间，减少重复值守，提高一致性和安全性，并形成可审计知识资产。 |
| 07 | 核心闭环？ | 输入 → 分类 → 上下文 → 诊断/计划 → 策略/审批 → 执行 → 验证 → 通知 → 复盘。 |
| 08 | 为什么 Multi-Agent？ | 广泛只读采集、专业判断、策略审批、最小写执行和独立验证需要不同上下文与凭据。 |
| 09 | MVP 边界？ | 复用现有 AgentTeams 原型，跑深一个场景：Docs 访问故障的正常分支、Fake Success、越权与未知输入分支，外加同一故障的输入变体集。 |
| 10 | 怎样算成功？ | 在未见过的输入变体上仍正确闭环；工具受角色权限约束；只有重新观测到解锁且 Docs 可访问才完成；认知环节经规则基线对照证明价值；全过程有 Trace/Evidence。 |

## 通用产品模型

### 任务定义：

任务按**谁发起、带着什么意图**到达。办公侧 IT 的发起方只有四个——员工、组织流程、监控系统、IT运维——涵盖的五类工作彼此不相干：

| 发起方 | 日常说法 | 这类工作的实质 | ITIL 对应 | 当前覆盖 |
| --- | --- | --- | --- | :---: |
| 员工·报障 | “我的这个文档显示没有权限访问，无法打开” | 症状已知、根因未知：救火与归因 | Incident | ✅ 身份/访问类 |
| 员工·申请 | “给我开个 VPN 账号” | 判断该不该给，开通并确认生效 | ServiceRequest | 设计映射 |
| 组织·人事变动 | “下周一有三个新人入职” | 批量同步：入职开通、转岗调整、离职回收 | LifecycleEvent | 设计映射 |
| 系统·告警 | 云容器监控报警 | 信号处置：确认影响面，通知或升级 | Alert | 设计映射 |
| IT·例行 | “季度权限审计到了” | 计划内变更与存量治理 | Change / 审计 | 设计映射 |

### 报障类细分：错误提示也是症状，断点在哪一层只有系统知道

员工不会说“我在 IAM 里的账号被锁了”，他们说“我的这个文档显示没有权限访问，无法打开”。这句话比“打不开”信息更多，但它仍然只是症状：屏幕提示是应用对底层失败的**翻译**，而应用经常翻译得很差——账号锁定、会话过期、权限过期、授权服务故障，在员工屏幕上都可能是同一句“没有权限”。它能把断点收窄到以身份、权限、应用为主的几层，但收窄不等于定位：

| 断点层 | 这句“没有权限”背后的真实形态 | 该层的系统记录（真相所在地） |
| --- | --- | --- |
| 身份 | 账号被锁或 SSO 会话过期，认证失败被渲染成“无权限” | IAM/SSO：账号状态、锁定原因 |
| 权限 | 应用权限确实缺失或已过期；个别情况是单个文档的共享被收回 | 应用授权：权限存在性与有效期 |
| 应用 | 授权/配置服务自身故障，往往多位同事同时报错 | 服务健康与监控 |
| 网络 | 远程或某网段连不上认证端点，报错文案失真 | VPN、网络设备与 DNS |
| 终端 | 仅本机浏览器凭据或缓存损坏，换台机器即恢复 | MDM、终端状态 |

诊断的实质就是**把症状——包括员工引述的错误提示——映射到层，再在该层的系统记录中定位根因**。没有任何一个后台能替你完成这个映射：IAM 只知道锁没锁，应用只知道有没有权限记录，谁也看不到对方，今天靠的是服务台人员脑内的经验路由。这也是惯性最容易出错的地方：把“提示没有权限”直接翻译成权限问题，或把“IAM 显示锁定”直接翻译成解锁——单信号都不构成诊断。OfficeOps 把跨系统上下文采集作为第一能力、首个场景选身份/访问类故障，正是因为它要同时取证四层、工单量在服务台统计中常年居前、且完成标准可外部观测（解锁 + 功能探测）。

各类工作不仅业务上不相干，**经验也无法迁移**：处理账号锁定积累的系统、节奏和风险感，对处理一批入职开通毫无用处。认知密度同样不同：**报障类步骤少而判断深（认知密集，最需要证据推理）；人事变动类步骤多而单步判断少（编排密集，规则即可承载）**。前者是 Agent 的价值区，这正是 MVP 先做报障类、把生命周期类留给场景包扩展的依据（见 DECISION-006）。

### 任务准入标准（边界防杂糅）

一个任务进入 OfficeOps，当且仅当同时满足：

1. **需要跨系统上下文**——单一后台控制台能解决的不进（那是厂商平台/RPA 的职责）；
2. **完成标准可外部重观测**——DesiredOutcome 能表达为新鲜状态读取 + 功能探测（“把文档写得更好”没有完成判据，不进）；
3. **动作空间有界可分级**——受控动作能列 allowlist 并定 L0–L3（“优化全网架构”无界，不进）。

### 管理对象：引用系统记录，不重建 CMDB

| 对象 | 系统记录 | OfficeOps 的增量 |
| --- | --- | --- |
| Person / Account / Group | IAM、HR | 引用 ID + 观测快照 |
| Device | MDM、CMDB | 引用 ID + 观测快照 |
| Application / Service | CMDB、监控 | 引用 ID + 观测快照 |
| NetworkEndpoint / Resource | CMDB | 引用 ID + 观测快照 |

OfficeOps 不维护对象主数据，只增量定义三样东西：**关系边**（依赖/归属/授权，构成 Operational Context Graph）、**Observation**（带来源与时间的观测）、**Evidence**（可回放证据）。这是“Agent Infra”的本义：任务态的跨系统上下文与证据层，不是又一套 CMDB。

### 场景包结构

```text
Scenario Pack
├── WorkItem schema / classifier
├── Agent routing policy
├── Skills
├── Tool capability requirements
├── Risk and approval rules
├── Verification assertions
├── Golden Cases
└── Knowledge / Runbook
```

通用核心不预先知道每台打印机或每个 VPN 厂商；场景包和 Adapter 负责把专业对象映射到核心模型。

## 首个可运行验证案例

### 输入

员工 Alice 在钉钉上报障：“我的这个文档显示没有权限访问，无法打开。”

### 提示指向权限，证据指向锁定

屏幕提示把矛头指向权限层，但诊断不采信翻译。Context Worker 五路取证，逐层排除后，真实断点在身份层：

- IAM：员工 active，账号 `locked=true`（`lock_reason=auto_lock`）——真实断点在身份层；
- VPN：enabled——排除网络层；
- 应用权限：Docs permission exists 且在有效期——排除权限层，屏幕上的“没有权限”是应用对认证失败的错误翻译；
- 服务健康：Docs healthy——排除应用层；
- 功能探测：Docs inaccessible——失败发生在应用访问层，不是单个文档的共享被收回。

### 闭环

Context Worker 采集证据 → Diagnosis Worker 排除权限/网络/应用，判断 `account_locked` → 风险策略校验 `lock_reason=auto_lock` 后允许受限解锁 → Remediation Worker 执行 → 使用新鲜 IAM 查询和 Docs 功能探测复验 → Manager 仅在两个后置条件都满足时完成。

### 输入不总是一句标准话术

同一故障会以不同说法到达：口语化、乱序、夹带无关信息或信息不全，甚至像本案例一样——屏幕提示把方向带偏。本案例与 G13 互为镜像——两者是“同症异因”（表面症状相同、真实根因不同）的两个方向：这里是提示说“没有权限”、真相是账号锁定；G13 是旧观测显示曾锁定、权威读取未锁，真相是权限过期——以最新鲜观测为准，不把陈旧信号当根因。因此成功标准不是“跑通一次 G01”，而是：同一底层故障的 10–20 个输入变体得到一致的正确处置，任何单信号都不构成诊断。规则解析器在第几个变体上崩溃，就是 LLM 认知环节价值的起点（对照实验见 10 评估计划）。

### 为什么它只是验证切片

它验证的是 OfficeOps 的公共能力：多源上下文、Agent 职责隔离、Skill/Tool 分层、MCP 权限隔离、执行后验证、Fake Success、Trace 和状态机。后续打印机、会议室、VPN 申请或云服务异常复用这些能力，但增加各自的场景 Schema、Skill、Policy 和 Adapter。

## MVP 不做什么

- 不在初赛同时实现打印机、钉钉、VPN、云和 Kubernetes 写入。
- 不声称已连接真实企业系统；厂商不可用时使用契约一致的 Sandbox。
- 不让一个 Agent 拥有所有系统读写权限。
- 不把 Tool 返回 `success=true` 当成完成。
- 不为了推荐技术数量而堆 Nacos、RocketMQ、数据库和 RAG。
- 不把 LLM 放进不需要判断的环节：策略与门禁是代码，不是提示词。
- 不承诺所有动作无人审批；风险策略决定自动、审批或禁止。

## 核心差异化

1. **跨域但不混乱**：统一任务与对象核心，场景包隔离专业差异。
2. **多 Agent 对应真实职责分离**：采集、判断、执行和验证的上下文/权限不同。
3. **验证优先**：成功由 Desired Outcome 与执行后的新鲜观测决定，执行者不能自证成功。
4. **能力可以复用**：Skill 是任务能力，Tool 是连接契约，Adapter 是厂商实现。
5. **经验可运营**：每次 Run 产生结构化 Evidence、评测样本和候选知识，而非只留聊天记录。
6. **开放而非绑定**：Agent Identity、Skill、Tool/MCP 与场景包均为可替换协议。商业 Agentic IT 平台（Atomicwork、ServiceNow、Atera、Freshservice）已验证方向，但能力绑定自家生态——OfficeOps 以比赛指定 AgentTeams 为基点提供开放参考实现。

## 决策记录

### DECISION-001 · 保持 OfficeOps 通用方向

- **选择**：覆盖企业数字办公 IT 运维，不改为单一 VPN/AccessOps 产品。
- **原因**：团队既有方向是从设备到协作平台的贯通；VPN/SSO/OA 经验是场景验证素材。
- **边界**：只有直接服务员工数字办公的系统和依赖进入 OfficeOps。

### DECISION-002 · 通用核心 + 场景包 + Adapter

- **选择**：稳定领域概念和协作协议，专业差异下沉到场景包及 Tool Adapter。
- **原因**：新增场景不应重写 Manager、Evidence、Approval、Execution、Verification 和 Trace。
- **失败退路**：新场景不能自然映射时建立新的有界上下文，而非无限增加通用字段。

### DECISION-003 · 架构广度与 Demo 深度分离

- **选择**：方案完整描述通用架构，工程只跑深一个 Docs 访问闭环。
- **原因**：比赛同时看行业复制性和端到端证据；接入数量不直接得分。
- **失败退路**：原型不稳定时保留本地确定性路径、运行证据和录屏。

### DECISION-004 · Tool Success 不等于 Task Success

- **选择**：每个场景包必须定义 DesiredOutcome 与独立 Verification Assertions。
- **原因**：工具回执、配置状态和用户体验可能不一致。
- **失败退路**：无法做功能探测时结果为 `INCONCLUSIVE`，不能伪报成功。

### DECISION-005 · 按风险自治

- **选择**：L0 只读自动；L1 可逆低风险动作可由策略自动；L2/L3 必须审批或禁止。
- **原因**：企业落地需要人类在环和职责分离，不能以“零人工”覆盖所有动作。

### DECISION-006 · 混合编排：认知环节是 Agent，安全链路是代码

- **选择**：策略/审批、Tool Gateway 校验、幂等与验证断言保持确定性工作流；输入规范化、上下文采集顺序、根因判断、路由与未知处理由模型自主决策。
- **原因**：关键合规流程需要可预测、可审计；自由文本理解与证据缺口判断无法穷举为规则。二者混在同一环节会同时失去安全性和灵活性。
- **失败退路**：某认知环节若在变体输入上不优于规则基线（见 10 的对照实验），该环节降级为代码，不保留装饰性 LLM。

## 复赛演进顺序

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| W1 | 稳定现有 Docs 访问原型、Schema 和 AgentTeams 运行方式 | 可重复安装、正常/异常/变体 Case、证据包 |
| W2 | 补 Policy/Approval、独立 Verification、Tool Gateway 门禁 | 审批记录、权限隔离、Fake Success/越权测试 |
| W3 | 接一个真实感更强的渠道或第二个只读适配器 | 钉钉/ITSM 输入或设备只读查询，不增加第二个高风险写域 |
